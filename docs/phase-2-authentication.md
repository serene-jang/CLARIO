# CLARIO 녹화 기능 추가 개발 프롬프트

현재 개발 중인 CLARIO 프로젝트에 **교사 대시보드 전체 화면 녹화 기능**을 추가해 줘.

## 1. 개발 전 필수 사항
- 먼저 기존 프로젝트의 `PRD.md`, `AGENT.md`, `TASKS.md`, `ARCHITECTURE.md`와 실제 코드를 모두 확인해.
- 현재 구현된 기능과 프로젝트 구조를 파악한 뒤 개발을 시작해.
- 기존 기능을 임의로 삭제하거나 변경하지 마.
- 기존 구조와 맞지 않는 부분이 있다면 먼저 이유를 분석하고, 필요한 변경 사항을 문서에도 반영해.
- 단순히 화면 디자인만 만들지 말고, 실제로 작동하는 기능을 구현해.

## 2. 핵심 녹화 기능

### 2-1. 녹화 대상
- 교사가 CLARIO에서 수업을 진행할 때 교사 대시보드 전체를 하나의 영상으로 녹화해.
- 대시보드에 표시되는 모든 학생의 실시간 화면 타일도 영상에 포함해.
- 학생별로 별도의 녹화 파일을 만들지 마.
- 학생이 여러 명 참여해도 교사 화면에서 보이는 전체 화면 구성을 하나의 영상으로 기록해.
- 녹화된 영상은 교사가 수업 중 확인할 수 있는 화면 배치와 최대한 동일하게 유지해.

### 2-2. 녹화 시작 및 종료
- 학생이 수업에 참여하면 녹화 시작 조건을 확인해.
- 단, 학생이 입장했다는 이유만으로 브라우저 권한이나 학교 정책을 무시하고 자동 녹화를 강행하지 마.
- 필요한 권한과 교사의 녹화 설정이 확인된 경우에만 녹화를 시작해.
- 같은 수업에서 녹화가 중복으로 시작되지 않도록 해.
- 교사가 수업을 종료하거나 녹화를 중지하면 녹화 파일을 정상적으로 마무리해.
- 녹화가 진행 중인지, 중지되었는지, 저장 중인지 교사가 확인할 수 있게 해.

### 2-3. Google Drive 저장
- 녹화가 끝난 영상은 교사의 Google Drive에 업로드해.
- Google Drive API와 OAuth 인증을 사용하고, 교사가 명시적으로 권한을 승인하도록 해.
- 업로드 진행률과 성공·실패 상태를 표시해.
- 네트워크 오류가 발생하면 재시도할 수 있도록 하고, 실패했다고 녹화 파일을 잃어버리지 않도록 해.
- 큰 영상 파일도 처리할 수 있도록 업로드 방식과 파일 크기 제한을 고려해.
- 인증 토큰이나 비밀 키를 프런트엔드 코드에 노출하지 마.

### 2-4. 영상 보관 및 삭제
- 영상은 교사가 직접 삭제하기 전까지 자동 삭제하지 않는 것을 기본 정책으로 해.
- 날짜, 수업명, 녹화 시간 등으로 영상을 구분할 수 있게 해.
- 교사가 녹화 목록에서 영상을 재생하거나 Google Drive에서 열 수 있게 해.
- 교사가 원하는 영상을 직접 삭제할 수 있도록 해.
- 공유 권한은 기본적으로 교사 본인 또는 학교에서 승인된 사용자에게만 허용하고, 공개 링크 공유를 기본값으로 설정하지 마.
- Drive 저장 공간 부족, 업로드 실패, 권한 만료 등의 문제를 교사에게 명확히 알려 줘.

## 3. 학생 화면 실시간 표시

- 학생용 CLARIO에서 수집이 허용된 학생 화면을 교사 대시보드에 실시간으로 표시해.
- 학생별 화면을 작은 타일로 배치하고, 교사가 특정 학생을 선택하면 해당 화면을 크게 볼 수 있게 해.
- 학생 화면을 대시보드에 표시하는 기능과 대시보드 녹화 기능을 분리해서 설계해.
- 실시간 화면 연결이 끊기거나 지연되면 연결 상태를 표시해.
- 학생별 개별 영상 파일을 생성하거나 저장하지 마. 녹화 대상은 교사 대시보드 전체 화면 하나야.

## 4. 기술 구조

기존 프로젝트의 기술 스택을 우선 확인하고, 그 구조에 맞춰 구현해.

필요한 구성요소는 다음과 같아.

- **학생 화면 캡처:** 브라우저 또는 Chrome 확장 프로그램 등, 실제 기기에서 권한을 받아 화면을 캡처할 수 있는 방식
- **실시간 전송:** WebRTC 및 필요한 시그널링 서버
- **연결 관리:** 학생 입장, 연결 상태, 권한 확인을 처리하는 백엔드
- **교사 대시보드:** 여러 학생의 실시간 화면을 타일 형태로 표시
- **대시보드 녹화:** 브라우저 화면 캡처 기능과 MediaRecorder 등으로 대시보드 전체를 영상으로 기록
- **Google Drive 연동:** OAuth 인증, 영상 업로드, 영상 목록 확인 및 삭제
- **상태 관리:** 녹화 시작·종료·업로드·오류 상태를 일관되게 관리

필요하다면 `screenCaptureService`, `recordingManager`, `videoRecordingService`, `googleDriveService` 등의 모듈로 역할을 분리해. 단, 기존 코드에 더 적합한 구조가 있다면 그 구조를 우선해.

## 5. 개인정보 및 보안

- 실제 학생 화면을 수집하고 녹화하기 전에 학교 관리자 승인, 기기 관리 정책, 필요한 브라우저 권한을 확인해.
- 학생과 교사에게 녹화 사실 및 관련 안내가 표시되도록 해.
- 학생 화면과 녹화 영상은 권한이 있는 사용자만 접근할 수 있도록 해.
- 수업 코드만으로 다른 수업의 화면이나 녹화 영상에 접근할 수 없도록 서버에서 권한을 검증해.
- 화면 수집과 녹화의 시작·종료 및 영상 열람 권한을 관리할 수 있도록 해.
- 불필요한 개인정보를 수집하거나 기록하지 마.
- 브라우저에서 허용되지 않는 화면 캡처를 몰래 실행하거나 권한 확인을 우회하지 마.

## 6. 오류 처리

다음 상황을 반드시 고려해.

- 학생 화면 캡처 권한이 없는 경우
- 학교 기기 정책 때문에 확장 프로그램 설치나 화면 캡처가 차단된 경우
- 학생 화면 연결이 끊어진 경우
- 녹화 중 브라우저나 네트워크에 문제가 발생한 경우
- Google Drive 인증이 만료된 경우
- 업로드가 실패하거나 저장 공간이 부족한 경우
- 교사가 실수로 녹화 화면을 닫으려는 경우
- 같은 수업에서 녹화가 중복 실행되는 경우

오류가 발생하면 원인을 이해하기 쉬운 문장으로 표시하고, 가능한 경우 복구 또는 재시도 기능을 제공해.

## 7. 테스트 및 완료 보고

- 녹화 시작과 종료가 정상적으로 작동하는지 테스트해.
- 여러 학생 화면이 하나의 대시보드 영상에 포함되는지 확인해.
- 학생별 녹화 파일이 별도로 생성되지 않는지 확인해.
- Google Drive 업로드, 영상 목록, 재생 및 삭제를 테스트해.
- 권한이 없는 사용자가 영상에 접근할 수 없는지 확인해.
- 기존 CLARIO 기능이 정상적으로 작동하는지도 회귀 테스트해.

## 공개 이메일·비밀번호 가입

교사 앱은 실제 가입·로그인 화면으로 시작한다. 학교 API·학교 이메일·학교 관리자
사전 승인 없이 누구나 이메일 계정을 만들고 본인 교실을 생성할 수 있다.
학생의 무계정 참여·교사 승인·본인 쿠키 경계는 변경하지 않는다.

운영자는 `DATABASE_URL`과 정확한 `APP_ORIGINS`를 함께 설정하고, DB 백업/변경
승인 후 `npm run db:migrate --workspace @clario/server`로 스키마 13을 적용한다.
API는 자동 마이그레이션하지 않는다. `GOOGLE_CLIENT_ID`는 선택 사항이다.
미설정이면 Google 버튼 없이 이메일 가입·로그인을 제공하고, 설정하면 기존
Google 서명·audience·nonce 검증을 유지한다. 학교별 API는 필요하지 않다.
실제 공개 Azure 서버/DB 변경이나 Google 설정은 이번 코드 작업에 포함하지 않는다.

가입은 `POST /api/identity/auth/email/register`에
`{email,password,displayName}`, 로그인은 `POST /api/identity/auth/email/login`에
`{email,password}`를 보낸다. 가입은 201, 로그인은 200이며 기존 Google과 같은
`{user,token,expiresAt,capabilities}`를 반환한다. 이메일은 trim/소문자로
정규화하지만 비밀번호는 공백을 포함해 원문을 유지하고 12~128자로 제한한다.
학교 ID/역할 입력으로 권한을 받지 못하며 독립 `member`로 생성된다.

비밀번호는 Node 비동기 scrypt(N=32768,r=8,p=3,32바이트 키)와 임의 16바이트
salt로 해시한다. 비밀번호·해시·토큰 원문은 감사 로그에 남기지 않는다.
1시간 세션은 토큰 해시만 DB에 저장하고 UI 메모리에서만 보관한다.
오류·비활성·세션 만료·로그아웃·교실별 권한 검사를 기존 경계에 연결한다.
존재하지 않는 계정도 동일 비용의 비밀번호 검증과 일반적인 401 오류를 사용한다.

스키마 13은 `users.password_hash`와 `identity_auth_budgets`를 추가한다.
이메일/IP별 고정 15분 창에서 각각 10/40회까지 가입·로그인 시도를 허용한다.
PostgreSQL의 원자적 갱신으로 서버 재시작/다중 인스턴스에도 한도를 공유하며,
프로세스별 해시 동시 실행은 4개로 제한한다. 만료 예산은 다음 요청 때 삭제한다.
IP는 소켓에서만 읽고 예산 키는 SHA-256 해시로 저장한다. 프록시 뒤 공유 IP
용량·정기 삭제는 공개 운영 전에 검증해야 한다. 임의 전달 IP 헤더는 신뢰하지 않는다.

**제한:** 이메일 소유 확인 메일·비밀번호 재설정·Google/이메일 계정 연결은
제공하지 않는다. 가입은 학교 소속/교사 자격이나 이메일 소유의 증명이 아니다.
확인되지 않은 이메일로 기존 권한을 부여하지 않는다. 동일 이메일 기존 계정은
새 가입으로 덮어쓰지 않고, Google 로그인에서도 이메일 계정과 자동 병합하지 않는다.
원래 가입한 방식으로 로그인해야 한다. 본인이 만든 교실의 관리 관계만 생성한다.

## 새 무로그인 학생 목표와 현재 상태

교사는 Google 또는 이메일로 로그인하고 학생은 계정 없이 코드·이름·학번으로 신청해 승인을 받는다. 4단계 신청/승인·복구·버전 8 공유 제한·5단계 학생 관리·6단계 수업/실제 연결·7단계 교실 자료에 이어 8단계 자율 집중 안내를 연결했다. 아래 Google 설명은 교사와 기존 계정 호환 경로다.

확정 정책은 교사 승인 필수·선택 명단 대조, 코드 12자/24시간, 정원 40/최대 100, 참여 시도 15분당 브라우저 10/IP 100회다. 이름은 NFC/trim 후 1~100자, 학번은 trim 후 ASCII 숫자 1~20자리·선행 0 유지다. 자격은 대기 최대 30분, 승인 후 유휴 2시간/절대 12시간이며 승인/복구 때 회전한다. 자격 생성은 신뢰된 내부 트랜잭션 함수이고 공개 발급 경로가 아니다.

### 학생 쿠키와 운영 연결 조건

- 학생 앱은 같은 원본 `/api/student/session` GET으로 본인 상태를 복원한다. 쿠키가 없으면 미참여이고 Google 요청을 하지 않는다. `/activate`·`/end` POST는 정확한 Origin/Host·JSON·자격 기반 CSRF를 검사한다. 자격 원문은 JSON이나 JS 저장소에 노출하지 않는다.
- HTTPS 쿠키는 `__Host-clario-student`, HttpOnly·Secure·SameSite=Strict·Path=/·Domain 없음이다. 비운영 localhost/127.0.0.1 HTTP에만 `clario-student-dev`를 사용한다. 브라우저당 한 교실이며 전환 전 종료한다.
- 개발은 기존 학생 Vite `/api` 프록시를 이용한다. `APP_ORIGINS`에 학생 웹의 실제 원본을 넣고 Host를 보존한다. Origin 없는 GET은 `Sec-Fetch-Site: same-origin`이 필요하므로 브라우저 밖에서 점검할 때는 정확한 Origin 헤더를 보낸다.
- **학생은 `VITE_API_BASE_URL`을 사용하지 않는다.** 현재 Azure 정적 웹과 API는 서로 다른 사이트다. 같은 원본 프록시·TLS/Host·Secure 쿠키를 구성/검증하기 전 운영 학생 참여가 가능하다고 표시하지 않는다. 교차 사이트 쿠키 허용이나 학생 Google 로그인으로 우회하지 않는다.
- 만료/철회·차단/퇴장·세대 불일치·종료/보관 교실은 거부한다. 유휴 갱신은 절대 만료를 늘리지 않는다. 종료는 자격·연결/출석·감사 변경이 모두 성공한 뒤 쿠키를 제거하고, 실패하면 성공 안내 없이 재시도한다.
- 교사 초대·학생 신청/승인·복구와 수업/웹 presence·교실 자료를 구현했다. 상태 복원/승인 성공 자체는 온라인·화면 공유 성공이 아니다.

**로컬 증거:** 앱 테스트 131개·배포 검증 2개 통과. 실제 학생 Vite 프록시의 Host 보존을 HTTP 회귀 테스트로 고정했다. 브라우저는 격리된 실제 PostgreSQL·API·Vite에서 제한 쿠키 복원·합성 승인 후 활성화/회전·새로고침·종료/퇴장·감사 반영·유휴 만료/개인정보 제거를 확인했다. HttpOnly JS 비노출·CSRF 누락 403도 확인했다. 승인 동작 자체는 fixture이며 실제 교사 OAuth·운영 HTTPS 프록시/쿠키 검증은 아니다.

## 재사용할 교사 인증과 현재 계정 기반 화면

- 교사 연결 화면에서 표시 이름을 입력하고 Google 로그인한다. 별도 비밀번호·작업공간·관리자 사전 계정 등록은 요구하지 않는다. 기존 사용자는 저장된 표시 이름을 유지한다. 학생 기본 앱은 이 경로를 사용하지 않는다.
- `/api/auth/config`·`/api/auth/challenge` 후 `POST /api/identity/auth/google`을 호출한다. 서버가 실제 Google 서명/audience/issuer/만료·이메일·nonce를 검증하고 Google sub 기준으로 독립 신원을 만들거나 조회한다.
- `GET /api/identity/me`, `GET /api/identity/classrooms`, `POST /api/identity/logout`을 제공한다. 생성 가능 자격과 현재 교실별 역할은 별개이며 신규 신원은 기존 조직 관리 API를 사용할 수 없다.
- 세션 토큰은 DB 해시·1시간 만료, UI 메모리 보관이다. 새로고침하면 재로그인한다. 401/만료 시 개인정보를 지우며 목록 오류·로그아웃 실패를 빈 목록/성공으로 숨기지 않는다.
- 다른 Google sub의 동일 이메일은 충돌이다. Google sub가 없는 기존 등록 이메일은 `LEGACY_LINK_REQUIRED`로 안내한다. **기존 작업공간 로그인·계정 연결**에서 검증 로그인한 후 새 로그인으로 돌아온다. 이메일만으로 기존 권한을 자동 연결하지 않는다.
- 버전 6은 기존 UUID/조직 역할·기기/자료 참조를 유지하고 독립 `member`·교실별 회원 관계와 초대/세션/연결 저장 기반을 추가한다. 기존 학생/교사 명부를 이전하며 현재 권한을 재검사한다. 100명 초과 기존 명부는 전체 전환을 실패시키므로 백업 후 정원을 먼저 조정한다. 자동 다운 마이그레이션은 없다.
- 로그인 후 교실·코드·선택 명단 관리와 신청 승인/복구·참여 학생 관리·수업 시작/종료·실제 연결 현황을 제공한다. 생성 자격과 기존 조직 관리자 범위는 별개이며 다른 교사의 교실을 관리할 수 없다.

### 학생 신청과 승인 사용법

학생은 코드·이름·학번으로 `POST /api/student/join`에 신청한다. 제한 쿠키로 본인 상태만 확인하며 명단 대조 결과·다른 학생 정보·관리 ID는 받지 않는다. 교사는 교실의 **신청 목록 다시 확인**(`GET /api/identity/classrooms/:id/requests`)으로 신청 종류/상태·명단 대조를 보고 본인을 직접 확인한다. 신청별 `/approve`·`/reject` POST는 현재 관리자만 수행한다.

복구는 학생이 명시적으로 선택하고 교사가 확인 후 `confirmRecovery:true`로 승인한다. 신청만으로 기존 학생 자격을 끊지 않는다. 승인 시 이전 자격/연결과 과거 미활성 승인 신청을 철회하고 새 자격은 본인 `/session/activate`에서 회전 전달한다. 거절·취소는 학생 상태에 표시하며 종료 후 재신청한다. 새로고침은 쿠키 기반, 상태 변경 확인은 수동이며 실시간이 아니다.

최근 15분 브라우저 10/IP 100/코드 100회, 교실 유효 대기 100건/30분이다. 서명 익명 브라우저 쿠키와 PostgreSQL 이벤트·잠금을 공유한다. IP/코드 원문은 저장하지 않고 HMAC 식별자만 저장한다. 15분 초과 이벤트는 다음 신청 때 삭제하므로 무요청 기간의 정기 물리 삭제는 운영 작업이다. 원문 IP는 소켓에서만 가져오고 전달 헤더는 신뢰하지 않는다. 운영 신뢰 프록시·공유 IP 용량/정기 삭제 검증은 별도다.

### 교실 자료와 학생 권한

교사는 **관리 열기 → 수업 자료 공유**에서 HTTPS 링크 등록/삭제·목록을 관리한다. 학생은 승인 후 `/api/student/materials`를 10초마다 조회하고 실제 수신한 목록의 최대 50개 식별자를 `/materials/received`로 확인한다. 명시적 자료 열기만 `/materials/:id/open`에서 현재 자격/승인/교실/만료를 재검사한다. 모든 학생 변경 요청은 기존 같은 원본·JSON·CSRF 경계를 사용하며 학생 ID나 Google 인증으로 우회하지 않는다.

버전 9 `classroom_material_receipts`는 기존 기기 전달 기록과 독립이다. 수신·열기 시각은 최초 성공 시각을 유지하며 읽기 완료가 아니다. 자료 목록에는 다른 학생 정보나 원문 URL을 보내지 않는다. 교사는 5초마다 현재 승인 참여자의 수신/열기 요청 수를 확인한다. 교사/학생 모두 최신순 50개 페이지와 서버 확인 시각을 제공하며 장애 시 마지막 결과/확인 불가, 권한 상실 시 비공개 정보 제거를 처리한다.

자료는 기존 7일 접근 만료를 유지한다. 수업 종료는 승인 자격/자료를 유지하지만 교실 종료·퇴장/차단·자격 만료는 학생의 새 접근을 차단한다. 교실 종료/보관 후에도 현재 관리자는 조회·삭제 가능하고 새 등록은 불가하다. 삭제는 자료와 기기/학생 수신 기록을 제거하며 감사를 보존한다. 만료는 자동 물리 삭제가 아니며 복사된 외부 주소·이미 열린 페이지는 회수할 수 없다. 실제 OAuth/운영 HTTPS 쿠키·외부 사이트 안전성/로딩·실기기 검증은 별도다.

### 실제 참여 학생 관리

교실 설정에서 **학생 목록 다시 확인**으로 `/api/identity/classrooms/:id/participants`를 조회한다. 선택 명단·신청과 별개인 실제 참여 기록이며 이름/문자열 학번 검색, 참여 상태 필터, 이름/학번/상태/승인 시각 정렬, 50명 페이지를 제공한다. 학번은 선행 0을 유지한 문자열 순서다. 실제 연결/마지막 확인은 별도 수업 현황에서 제공하며 승인됨은 온라인이 아니다. 신청 검색/정렬은 조회된 최대 200건 범위다.

퇴장/차단은 학생 이름·학번 확인과 체크박스 후 참여자별 `/remove`·`/block` POST에 `{confirm:true,expectedGeneration}`을 보낸다. 최신 세대·현재 교실 관리 권한·열린 교실을 서버에서 확인한다. 상태/세대 변경·동일 학번의 기존 대기/미활성 승인 취소·제한/참여 자격 철회·연결/출석 종료·대상 감사를 원자 저장한다. 반복 동일 상태는 멱등이며 차단→퇴장은 거부한다. 오래된 화면의 세대 충돌은 409 후 재확인한다.

학생은 기존 자격으로 다음 요청부터 401을 받고 새 복구 신청 후 교사가 다시 확인해야 한다. 과거 복구 신청이나 일반 중복 신청으로 이를 우회하지 못하며 다른 학번의 동일인 완전 차단은 보장하지 않는다. 종료/보관 교실은 읽기만 제공한다. 관리/승인 후 서로의 목록을 무효화하고, 저장 성공/재조회 실패·네트워크 오류의 마지막 확인 결과·권한 오류의 개인정보 제거를 구분한다. 버전 8 저장 구조를 재사용하며 새 마이그레이션은 없다.

### 수업·실제 연결 현황

교실 관리의 **수업 시작**은 `/api/identity/classrooms/:id/lesson/start`에 빈 JSON을 전송하고 활성 수업 하나를 만든다. 교사 `/lesson` 조회는 5초마다 현재 권한을 확인하고 승인 학생의 실제 서버 마지막 확인/상태·집계를 반환한다. 학생은 같은 원본 `/api/student/lesson`에서 본인 수업만 10초마다 확인하고, 활성 수업이면 `/heartbeat`에 `{sessionId,connectionId,sequence}`와 본인 쿠키/CSRF를 보낸다. 연결 UUID는 탭/수업마다 다르고 타 학생 정보/자격 원문은 반환하지 않는다.

서버 시각 기준 20초 미만 온라인, 20~45초 재연결, 45초 이상 오프라인이다. 하나 이상의 유효 탭이면 학생 한 명으로 집계한다. 요청 제한 시간은 5초이며 정상 응답의 교사 반영 목표는 조회 5초+응답 5초다. 오류/시간 초과는 서버 확인 불가이고 과거 결과를 현재 접속 상태로 표시하지 않는다. 브라우저 절전/백그라운드 탭은 타이머 지연으로 재연결/오프라인이 될 수 있다. 웹은 탭 종료 알림 없이도 45초 lease 만료로 정리한다.

교사 종료는 확인 체크박스와 `/lesson/end`의 `{sessionId,confirm:true}`가 필요하다. 코드·대기/제한 자격·집중·해당 수업 연결/출석을 종료하고 감사를 저장하되 승인 관계/활성 참여 쿠키는 유지한다. 다음 수업은 유효 자격을 재검사해 코드 없이 연결한다. 수업 변경 ID·역순 이벤트·자격 세대를 검사하므로 과거 종료/heartbeat가 새 수업을 되살리거나 끊지 못한다. 교실 종료/퇴장/차단은 이와 달리 참여 자격까지 철회한다.

학생별 최근 1분 성공한 수업 요청 240회·동시 유효 탭 16개를 DB에서 공유 제한한다. 수업/lease도 PostgreSQL 원본이므로 별도 push 플랫폼이나 서버별 온라인 메모리 카운터를 사용하지 않는다. DB 버전 8을 재사용한다. 실제 OAuth·운영 TLS/동일 원본 프록시·운영 부하/절전·정기 개인정보 삭제 검증은 남아 있다.

### 교실 설정·초대·명단 경로

접두사는 `/api/identity/classrooms`다. `POST /`는 개인 교실·직접 관리자·초기 12자/24시간 코드를 원자 저장한다. `GET/PATCH /:id`는 관리 교실 설정·코드 메타데이터·선택 명단 조회/설정 변경, `POST/DELETE /:id/invitations`는 코드 재발급/폐기다. `GET/POST /:id/roster`, `PATCH/DELETE /:id/roster/:entryId`는 교실 범위 명단만 변경한다. 자동 승인·소유자/역할 변경은 제공하지 않는다.

`POST /:id/close`·`/:id/archive`는 코드·대기·자격/연결·기기 토큰/페어링·활성 세션을 종료하고 집중 안내를 해제한다. 기록을 삭제하거나 승인 관계를 임의 삭제하지 않는다. 관리자만 `?includeInactive=true` 목록으로 종료/보관 교실을 다시 확인한다. 다시 열기는 현재 제공하지 않는다. 기존 학급 보관도 같은 정리를 사용하되 기존 기기 명부 삭제 동작은 보존한다.

원문 코드는 발급 응답/UI 메모리에서만 보이며 목록/재조회·감사·영구 브라우저 저장에 남지 않는다. 명단은 NFC 이름·문자열 학번/선행 0을 보존하며 실제 학생 참여자와 별개다. 코드 관리 성공은 학생 연결 성공이 아니다.

실제 임시 PostgreSQL의 이전/rollback·동시 로그인·권한·세션 시험과 loopback HTTP 경로를 검증한다. 브라우저 로그인/빈 목록/로그아웃 렌더링도 합성 Google/API로 확인했다. **실제 Google 클라이언트·계정 E2E 및 운영 DB 적용은 아직 미검증**이며 테스트 대역은 운영 시작 경로에서 선택할 수 없다.

## 기존 작업공간의 구현 범위와 검증 구분

- Google Workspace 및 개인 Google 계정으로 로그인할 수 있다. Google OAuth client 설정에서 External 사용자 접근을 허용해야 한다.
- 교사 앱에서 가입자가 작업공간 이름과 표시 이름을 입력해 가입하면 해당 사용자가 작업공간 최초 관리자가 된다.
- 이메일의 Google 소유 확인은 로그인한 Google 계정을 증명할 뿐 학교·교직원·학생 신분이나 학교의 작업공간 소유권을 증명하지 않는다.
- 사용자 역할은 Google 계정이나 브라우저의 역할 입력에서 추론하지 않는다. 서버 DB의 승인된 역할만 적용한다.
- 작업공간 관리자는 이메일 도메인과 관계없이 교사·학생을 등록하고 역할·이용 상태를 관리할 수 있다. 초대 이메일 발송은 구현하지 않았다. 등록한 이메일을 당사자에게 안전하게 전달해야 한다.
- 교사는 담당 학급을 만들고 이름 변경·보관 처리하며, 관리자가 해당 작업공간에 등록한 학생을 학급에 등록·제외한다.
- 학생은 자신의 작업공간과 등록 학급만 본다. 학생은 학급 구성원 API와 전체 사용자 API를 사용할 수 없다.
- 기존 계정의 조직 소속은 하나로 유지한다. 새 직접 교실 회원 관계는 사용자 소속 이동/복제 없이 조직 경계를 넘을 수 있다. 실제 초대 수락/만료 API와 학교 신분 검증은 미구현이다.

실제 PostgreSQL에서 API·권한·세션 테스트를 수행한다. 테스트의 Google 신원 검증 경계는 가짜 서명 토큰을 허용하는 주입형 테스트 대역이며 운영 시작 경로에서는 선택할 수 없다. 운영 경로는 `google-auth-library`를 통한 실제 ID 토큰 검증만 사용한다.

**실제 Google OAuth 클라이언트와 계정이 아직 설정되지 않아 실제 Google 로그인 브라우저 E2E는 미검증이다. 공개 가입 코드 구현이 Google 클라이언트 생성/설정을 대신하지 않는다.** 화면 확인·녹화는 미구현이다.

## 로컬 PostgreSQL 준비

### 초기 설정 입력 화면

루트에서 `npm run setup`을 실행하고 터미널의 전체 주소(`http://127.0.0.1:5180/#...`)를 엽니다. Google 웹 OAuth 클라이언트 ID·작업공간 이름·관리자 이메일·표시 이름과 이메일 도메인(메타데이터)을 입력합니다. 실제 Google Cloud 프로젝트/승인 원본은 아래 안내대로 먼저 준비해야 합니다.

- 입력값을 서버에서 검증한 뒤 개발 DB 시작 → 버전 11까지 마이그레이션 → 로컬 작업공간·최초 관리자 등록 → `server/.env` 저장을 수행합니다. 독립 교사 로그인에는 작업공간 등록이 불필요하므로 아래 수동 설정을 이용할 수 있습니다.
- 동일한 학교·활성 관리자 정보로 재시도할 수 있지만, 기존 관리자·역할·학교 이름을 바꾸거나 이용 중지 계정을 복구하지 않습니다.
- 환경 파일의 다른 설정은 보존합니다. 기존 외부 DB 또는 다른 포트·허용 원본 설정이 있으면 중단합니다. DB 적용 후 파일 저장이 실패하면 부분 완료를 알리고 동일 정보 재시도를 안내합니다.
- DB 비밀번호는 서버가 생성한 로컬 연결 파일에서 읽으며 브라우저로 전송하지 않습니다. Client secret도 필요 없습니다.
- 설정 서버는 별도 명령으로 loopback에만 바인딩하며, 정확한 Host·Origin과 실행마다 바뀌는 토큰을 확인합니다. 공개 Backend에는 해당 경로를 연결하지 않습니다. 운영 환경에서는 실행을 거부합니다.
- 설정 성공 뒤에도 DB가 필요하므로 터미널을 유지하세요. API가 이미 실행 중이면 원래 터미널에서 재시작하고 교사·학생 웹을 실행합니다. 다음 실행에는 아래 `db:local` 명령을 사용하면 됩니다.
- 실제 학교 OAuth 성공, Chromebook 설치 및 공개 사이트 배포는 별도 검증입니다.

아래 수동 명령은 입력 화면을 사용하지 않을 때의 대안입니다.

Node.js 24, npm 11을 사용한다. 루트에서:

```powershell
npm install
npm run db:local --workspace @clario/server
```

개발 전용 portable PostgreSQL이 `127.0.0.1:55432`에서 실행된다. 해당 터미널은 유지한다. 비밀번호는 실행 시 무작위 생성되며, 데이터와 연결 정보는 Git에서 제외된 `server/.local-postgres/` 안에 보관된다. 이미 사용하는 55432 포트의 프로세스를 임의로 종료하지 말고 기존 PostgreSQL을 사용하거나 충돌을 해소한다.

이 도구는 `embedded-postgres`의 고정된 개발용 버전을 사용한다. 시스템 서비스나 OS 사용자를 생성하지 않는다. 운영 DB 대체물이 아니며, Windows 종료 시 라이브러리가 프로세스를 강제 종료할 수 있으므로 개발·합성 데이터에만 사용한다. CI도 별도 임시 클러스터만 생성하고 종료·삭제한다.

다른 터미널에서, 기존 `server/.env`가 없다면 연결 정보를 복사한다. 기존 파일이 있으면 덮어쓰지 말고 필요한 값을 병합한다.

```powershell
Copy-Item server\.local-postgres\connection.env server\.env
```

그 파일에 아래 설정을 추가한다.

```dotenv
PORT=4000
GOOGLE_CLIENT_ID=YOUR_WEB_CLIENT_ID.apps.googleusercontent.com
APP_ORIGINS=http://127.0.0.1:5173,http://127.0.0.1:5174
```

Google 설정은 공개 웹 클라이언트 ID만 필요하다. ID 토큰 로그인 방식이므로 OAuth client secret, Google access/refresh token, Drive/Classroom 권한은 필요하지 않다.

새 독립 로그인에 필요한 마이그레이션:

```powershell
npm run db:migrate --workspace @clario/server
```

기존 작업공간 기능도 이용할 때만 최초 관리자를 추가한다:

```powershell
npm run school:create --workspace @clario/server -- "학교 이름" school.example admin@school.example "관리자 이름"
```

`school.example`은 형식 예시다. 조직 도메인은 메타데이터이며 학교 소속 증명이 아니다. 독립 로그인은 개인 Google 계정도 가능하다. 명령은 기존 학교·계정·역할을 덮어쓰지 않으며 중복이면 실패한다. 데이터베이스 운영 권한이 있는 담당자만 이 명령을 실행해야 한다.

마이그레이션 버전은 DB에 저장되며 재실행 가능하다. 향후 스키마 변경은 이미 적용한 버전을 수정하지 말고 새 버전으로 추가해야 한다.

### 학생 기기 명부 등록 (추가 기능)

관리자 또는 담당 교사가 **학급 관리 → 학생 기기 등록**에서 다음을 입력한다.

- 기기를 사용할 학생: 해당 학급의 승인된 활성 학생 중 선택.
- 기기 이름: 앞뒤 공백을 제외한 1~100자.
- 학교 자산번호: 앞뒤 공백을 제외한 1~100자. 같은 학교에서는 대소문자만 다른 번호도 중복으로 처리한다.

저장은 서버 응답을 확인한 뒤 성공을 안내한다. 저장 실패 시 입력값을 보존하고 오류를 표시한다. 목록 조회 실패는 빈 목록과 구분하며 재시도할 수 있다. 잘못 등록했다면 등록 해제 후 다시 등록한다.

DB 마이그레이션 **버전 2**가 `registered_devices`와 학교별 자산번호 고유 인덱스를 추가한다. 버전 1은 수정하지 않는다. 기존 데이터베이스에도 다음 명령을 실행하고 API를 시작한다.

```powershell
npm run db:migrate --workspace @clario/server
```

명부 도입 시 버전은 2이며 현재 자료 수신 기록·집중 안내·학생 삭제 요청 승인 게이트를 포함한 API는 **버전 11**까지 적용해야 시작한다. API 전용 인증 설정은 유지하며 선택형 동일 원본 웹 제공에는 `SERVE_WEB=true`를 사용한다. DB별 난수 공유 비밀은 버전 8 마이그레이션에서 생성한다. 학생 삭제 요청은 접근 철회/정책 대기이며 실제 삭제 완료가 아니다. [최신 기기 연결 안내](./device-client.md)와 [현재 운영 절차](./azure-deployment.md#현재-1011단계--로컬-운영-준비)를 참고한다.

### 8단계 자율 집중 안내

교사 `GET/PATCH /api/identity/classrooms/:id/focus`와 학생 `GET /api/student/focus`를 제공한다. 변경은 현재 수업 ID/예상 버전으로 충돌을 방지하고 학생은 본인 승인 쿠키로 읽기만 가능하다. 기존 boolean을 공유하고 버전 10 트리거가 실제 변경 시 버전/시각을 올린다. 기본 꺼짐, 수업/교실 종료 시 원자적 해제·감사, 다음 수업 꺼짐이다. 교사 5초/학생 10초 전체 조회·5초 요청 제한·실패/오래된 결과의 확인 불가·권한 상실 시 비공개 상태 제거를 처리한다. 학생 준수 확인/행동 감시·차단·화면 캡처는 하지 않는다.

| API | 권한/동작 |
|---|---|
| `GET /api/classes/:classId/devices` | 담당 교사 또는 같은 학교 관리자만 기기 명부 조회 |
| `POST /api/classes/:classId/devices` | `studentId`, `name`, `assetNumber` 검증 후 저장. 학교는 서버 세션 기준 |
| `DELETE /api/classes/:classId/devices/:deviceId` | 해당 학급 범위에서 명부 등록 해제 |

- 학생·다른 교사·다른 학교 사용자는 명부 조회/등록/삭제가 차단된다.
- 기기 등록·해제는 감사 기록에 남긴다. 학생을 학급에서 제외하면 해당 학급의 기기 등록도 삭제하고 해제 감사 기록을 남긴다.
- 학급 보관 시에도 관련 기기 명부를 해제하고 감사 기록을 남긴다. 학생/학급 데이터는 기존 보관 동작을 유지하며, 해제된 자산번호는 다시 등록할 수 있다.
- 한 학생에게 여러 기기를 등록할 수 있지만 동일 자산번호를 여러 학급에 중복 등록할 수 없다.
- 자산번호는 사람이 입력한 명부 값이며 실제 하드웨어 인증 근거가 아니다. 비밀번호·키를 입력하지 않는다.
- 최초 명부 등록만으로는 `unknown`, 화면/녹화 지원은 `unverified`다. 후속 기기 페어링/heartbeat가 있으면 서버 수신 시각을 기준으로 연결 상태를 반환하며, 하드웨어 실물 인증을 의미하지 않는다.
- 실제 Google 계정 로그인 및 Chromebook 자동 연결은 여전히 별도 검증 대상이다.

추가 검증: 실제 임시 PostgreSQL에서 저장/중복/입력 검증·권한 격리·API 인스턴스 간 조회·등록 해제/학생 제외 연쇄 삭제·감사 로그·마이그레이션 재실행을 시험한다. UI 테스트는 저장·등록 해제·입력값 보존·조회 실패/재시도·빈 학생 목록·학급 관리 화면 연결을 다룬다.

```powershell
npm run dev:server
npm run dev:teacher
npm run dev:student
```

각각 별도 터미널에서 실행한다. 개발 앱의 `/api` 요청은 Vite가 로컬 API 4000 포트로 전달한다. API 포트를 변경하면 두 Vite proxy 대상도 조정한다. 프런트엔드를 직접 다른 API에 연결하려면 각 앱의 `.env.example`을 `.env`로 복사하여 `VITE_API_BASE_URL`을 설정한다.

## Google Cloud / OAuth 준비

1. 소유하거나 관리할 수 있는 Google Cloud 프로젝트에서 Google Auth Platform 브랜딩과 동의 화면을 설정한다. 개인·공개 사용자 이용을 위해 앱 대상 사용자를 **External**로 설정한다.
2. **웹 애플리케이션 OAuth 클라이언트**를 만든다.
3. 승인된 JavaScript 원본에 사용하는 교사·학생 원본을 정확히 등록한다. 로컬 예: `http://127.0.0.1:5173`, `http://127.0.0.1:5174`. localhost로 접속하려면 해당 원본도 별도로 등록한다.
4. Google의 로컬 origin 허용 조건은 클라이언트 설정에서 확인한다. IP 원본이 거부되면 `http://localhost:5173`, `http://localhost:5174`를 사용하고 `APP_ORIGINS`에도 동일하게 추가한다.
5. 게시 전 시험 상태라면 Google 동의 화면의 테스트 사용자에 로그인 계정을 추가한다. 공개 배포 때는 Google의 검증·게시 요건과 요청 범위를 확인한다. Google Workspace에서 조직 관리자가 OAuth 앱을 제한하면 해당 계정은 관리자의 승인이 여전히 필요할 수 있다.
6. 웹 클라이언트 ID를 서버 `GOOGLE_CLIENT_ID`에 설정한다. 이 구현은 GIS ID 토큰 callback 방식이며 서버 OAuth redirect URI나 client secret을 요구하지 않는다.
7. 교사 앱에서 최초 Google 로그인과 작업공간 만들기를 선택한다. 작업공간 이름/사용자 이름을 입력하면 해당 사용자에게 작업공간 관리자 권한을 부여한다.
8. 관리자는 작업공간 구성원 관리에서 교사·학생 이메일을 등록하고, 교사는 학급 생성 및 등록 학생 연결을 수행한다. 학생은 학생 앱에서 본인 Google 계정으로 로그인한다.

개인 Gmail 및 다른 Google 도메인을 지원한다. 검증된 Google 이메일과 subject를 계정에 연결하며 `hd` 도메인을 학교 소속 판정에 사용하지 않는다. Google OAuth 앱의 시험 사용자 제한과 학교/조직의 Google 정책은 별도로 적용될 수 있다.

참고:

- [Google Identity Services 웹 로그인](https://developers.google.com/identity/gsi/web/guides/overview)
- [서버 ID 토큰 검증](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- [Google Workspace 앱 접근 관리](https://support.google.com/a/answer/7281227)

## 세션과 접근 통제

- 서버가 5분 유효한 단일 사용 challenge와 nonce를 생성한다. Google 검증 결과의 nonce가 일치해야 로그인된다.
- 서명·issuer·audience·만료는 Google 라이브러리로 검사하며, 검증된 이메일과 Google subject를 작업공간 구성원에 연결한다. Consumer 계정은 `hd`를 제공하지 않을 수 있으므로 조직 증명에 사용하지 않는다.
- 최초 작업공간 가입 시 서버가 새 작업공간과 관리자 계정을 원자적으로 생성한다. 학교명, 작업공간, 역할은 클라이언트가 기존 사용자 로그인에서 선택할 수 없다. 이메일 중복은 거부한다.
- 공개 가입은 프로세스별 IP 버킷 15분당 10회로 제한한다. 다중 인스턴스 운영에서는 게이트웨이/WAF 또는 공유 저장소 기반 rate limit을 추가해야 한다.
- CLARIO 세션은 무작위 256비트 opaque bearer token이다. DB에는 SHA-256 해시만 저장하고 만료는 서버 기준 1시간이다.
- 토큰은 React 메모리에만 보관한다. localStorage/sessionStorage, URL, 쿠키에 저장하지 않는다. 새로고침·탭 종료 시 다시 로그인해야 한다.
- 로그아웃은 서버 세션을 삭제한다. 계정 이용 중지·역할 변경은 해당 계정의 모든 세션을 삭제한다. 매 요청마다 현재 DB 역할·활성 여부를 다시 확인한다.
- 기존 교사/작업공간 API는 bearer 인증을 사용하므로 cross-site cookie 허용에 의존하지 않는다. 학생 API는 위의 별도 같은 원본 쿠키·CSRF 경계를 사용한다. 명시된 origin만 CORS로 허용한다.
- 로그인 API는 socket별 600회/분, 최대 1,000개 socket bucket으로 제한한다. 신뢰할 수 없는 forwarded IP는 사용하지 않는다. 공유 프록시 환경에서는 제한이 함께 적용되므로 운영 규모별 프록시·분산 rate limiting 검토가 필요하다.
- 다른 학교나 담당하지 않는 학급에 대한 요청은 리소스 존재를 누설하지 않도록 404로 응답한다. 학생의 관리 API 접근은 403이다.
- DB 외래 키로 학교 범위 일치를 추가 강제하고 SQL은 파라미터 바인딩을 사용한다.
- 로그인/로그아웃, 계정 승인·권한 변경, 학급 변경·등록/해제, 차단된 접근은 감사 기록에 남긴다. 토큰, nonce, Google credential은 기록하지 않는다.
- API 응답은 `Cache-Control: no-store`를 사용하며 민감한 내부 오류를 사용자에게 반환하지 않는다.
- 외부 PostgreSQL 연결은 인증서 검증이 켜진 TLS를 사용한다. 로컬 loopback만 암호화하지 않는 연결을 허용한다.

## 주요 API

기본 접두사: `/api`. 오류: `{ "error": { "code": "...", "message": "..." } }`.

| 메서드/경로 | 접근 | 설명 |
|---|---|---|
| GET `/auth/config` | 공개 | 공개 Google client ID |
| POST `/auth/challenge` | 공개 | 로그인 nonce 발급 |
| POST `/auth/google` | 공개 | `{challengeId, credential}` 검증 후 세션 발급 |
| GET `/auth/me` | 로그인 사용자 | 본인 정보 |
| POST `/auth/logout` | 로그인 사용자 | 현재 세션 폐기 |
| GET `/school` | 로그인 사용자 | 본인 학교 |
| GET/POST `/users` | 학교 관리자 | 같은 학교 계정 목록·승인 |
| PATCH `/users/:userId` | 학교 관리자 | 교사·학생 역할·활성 변경, 세션 철회 |
| GET `/classes` | 로그인 사용자 | 역할별 허용 학급 |
| POST `/classes` | 교사 | 본인 담당 학급 생성 |
| PATCH/DELETE `/classes/:classId` | 담당 교사·학교 관리자 | 이름 변경·보관 |
| GET/POST `/classes/:classId/members` | 담당 교사·학교 관리자 | 등록 학생 목록·등록 |
| DELETE `/classes/:classId/members/:studentId` | 담당 교사·학교 관리자 | 학급 등록 해제 |

관리자 계정 신규 생성·관리자 역할 변경은 웹 API로 허용하지 않는다. 초기 관리 명령은 별도 운영 권한을 전제로 한다.

## 배포와 개인정보 주의

- 이번 개발에서 Azure 설정 변경·유료 DB 생성·GitHub push·재배포는 수행하지 않는다.
- 기존 배포는 환경변수 세 개가 모두 없을 때 `/health`만 정상이며 `/api`는 503으로 로그인 미설정을 표시한다. 일부만 설정하면 서버가 명시적으로 시작 실패한다.
- 실제 배포에는 별도로 승인된 PostgreSQL, 마이그레이션/학교 등록, API 환경변수, 두 프런트엔드 빌드의 `VITE_API_BASE_URL`, Google 승인 원본이 필요하다.
- 환경변수와 DB 연결 문자열은 Azure 비밀 설정으로 관리한다. DB 비밀번호를 GitHub 변수나 프런트엔드 `VITE_` 값에 넣지 않는다.
- 마이그레이션/학교 등록은 DB 연결이 가능한 승인된 운영 환경에서 수행한다. 예: 서버 빌드 디렉터리에서 `node dist/manage.js migrate`, `node dist/manage.js school ...`.
- DB 계정·이름·이메일·학교·역할·학급 등록, Google subject, 세션 해시와 만료, 감사 메타데이터를 저장한다. Google access token, 비밀번호, 화면 내용은 수집하지 않는다.
- 만료된 challenge·세션은 다음 로그인 challenge 생성 시 정리한다. 주기적 정리, 계정/감사 보관 기간·삭제 및 백업 정책은 아직 운영용으로 완성하지 않았다.
- 실제 학생 데이터 사용 전 학교의 개인정보 처리 근거·고지·계정 승인·DB 백업·보관 정책을 검토해야 한다.
